# Housing Minister (working title: "Zoned Out")

A playable, browser-based housing-policy simulator. The player is a provincial housing minister steering a stylised pixel-art city through a 5-year term. Underneath the game is an agent-based model (ABM) of short-term rentals (STRs), long-term rentals, owners, and developers, **calibrated to the causal estimates from my earlier project** ([bc-str-ban-analysis](https://github.com/haji5/bc-str-ban-analysis), BC Bill 35).

## 1. Why this project exists (so decisions stay aligned)

**Career goal.** Land economist / data-science / policy-analytics jobs (economic consulting, BC and federal policy shops, tech-economist roles at marketplaces). The first project shows causal inference and data engineering. This one must show *different* muscles:

1. Building and calibrating a structural/agent-based model, not just estimating reduced-form effects.
2. Validating a model honestly (including testing whether my own DiD design recovers truth inside the model).
3. Shipping real software: typed code, tests, CI, a deployed playable site.
4. Communicating uncertainty to non-experts through a game.

**The hook (one sentence for interviews).** "I built a simulator calibrated to my own causal estimates, and then used it to test whether my difference-in-differences design recovers the true effect when displaced hosts can substitute into exempt areas."

**The lesson the game teaches.** Policy can move the thing it targets (STR listings fell ~32% in covered areas) while the thing people care about (rents) barely moves, or moves by an amount too small to detect. The player discovers this by playing, and the debrief shows what the data could and could not have told them.

### Non-goals

- Not a forecast, not policy advice, not a faithful digital twin of Victoria. It is a calibrated, simplified model. Say so in the UI and README.
- No backend, accounts, or databases at runtime. Static site only.
- No multiplayer. (Shareable seeds via URL are a stretch goal.)
- No copyrighted art, fonts, or sounds. All art is original and generated by code in this repo.

- **Preact** for UI panels (small, no heavy framework), **Canvas 2D** for the isometric map (zero-dependency; hide it behind a `Renderer` interface so PixiJS could replace it later), **D3** for charts (already familiar from the first project).
- **Vitest** (unit/property tests), **fast-check** (property tests), **Playwright** (smoke test + screenshots for visual iteration).

## 4. Time, scale, and scenarios

- **Tick = 1 month. Turn = 1 quarter (3 ticks).** A run is 20 turns (a 5-year term), configurable.
- **Scenario "Victoria 2023"** (primary): starts Sep 2023, pre-announcement. A **"Historical Bill 35" preset** applies the real policy calendar and must reproduce the calibrated history. The player can instead choose their own levers.
- **Scenario "Vancouver 2023"** (stretch, M8): Vancouver already had a 2018 bylaw and listings did *not* shrink (entire homes +4.9% by Jun 2026). It is a natural contrast scenario: same lever, different baseline.
- **Scale factor** `SCALE` (default 0.2, i.e. 1 agent per 5 real units) is a config constant, so dwellings ≈ 35,000 and renter households ≈ 13,000. Verify noise is acceptable and runtime budgets hold (section 11). All targets are scaled by `SCALE` before comparison.
- **Zones.** 8 stylised zones mapped to real geography in `docs/ASSUMPTIONS.md`, with attributes `covered` (principal-residence rule applies), `zoningCapacity`, `amenity`, `strDemand`. At least 3 are exempt (Juan de Fuca-like, Gulf Islands-like, and Salt Spring-like with a dated opt-in). The map is a tile grid with zones as districts.

## 5. Simulation model specification

Functional forms below are **v1 proposals**. the coding agent may change them, but every change needs a short ADR in `docs/adr/` and must keep the calibration pipeline working. Specify each equation in `docs/ODD.md` as implemented.

### 5.1 Determinism and common random numbers (non-negotiable)

- All randomness comes from a **counter-based hashed RNG**: `u = hash(seed, agentId, tick, purposeCode) -> [0,1)`. No shared stateful stream.
- Reason: when a lever changes, other agents' random draws must *not* shift. That gives **common random numbers**, so "your policy vs. no policy" is a low-variance paired comparison.
- Same seed + same params + same policy ⇒ bit-identical outputs. Tested.
- Iteration order of agents is fixed (ascending id). No reliance on object key order or `Map` iteration side effects.

### 5.2 State

```ts
type Tenure = 'OWNER_OCC' | 'LTR' | 'STR' | 'VACANT' | 'CONSTRUCTION';
type HostClass = 'SMALL_SINGLE' | 'SMALL_MULTI' | 'COMMERCIAL';

// struct-of-arrays in practice; shown as objects for readability
interface Dwelling {
  id: number; zone: number; tenure: Tenure; hostClass: HostClass | null;
  principalResidenceOfOwner: boolean;   // owner lives here; home-sharing stays legal
  rent: number;                         // current rent if LTR (sitting-tenant rent)
  tenantId: number | null;
  registered: boolean;                  // has registry number (after Phase 2)
  monthsInTenure: number;
  completionTick?: number;              // if CONSTRUCTION
}
interface Household {
  id: number; income: number; dwellingId: number | null;
  searchMonths: number; status: 'HOUSED' | 'SEARCHING' | 'DOUBLED_UP' | 'GONE';
}
interface Zone {
  id: number; name: string; covered: boolean; optInTick?: number;
  capacity: number;        // max dwellings allowed by zoning
  marketRent: number;      // current asking rent for new leases
}
```

### 5.3 Tick order (fixed)

1. **Exogenous update**: net migration inflow (scenario path + shock cards), interest-rate path, new household arrivals.
2. **Policy update**: apply lever changes effective this tick; update detection probability, fines, registry status; apply de-listing at Phase 2.
3. **Host decisions** (`hosts.ts`): each eligible dwelling reviews its use with probability `pReview` per month.
4. **Developers** (`developers.ts`): new starts; completions from the pipeline.
5. **Rental market** (`rentalMarket.ts`): searching households match to vacant LTR units; update zone market rents; update sitting-tenant rents on anniversaries.
6. **Households** (`households.ts`): stress, doubling-up, out-migration.
7. **Observe** (`observe.ts`): record true state and the researcher-view signals; at quarter end, emit a "snapshot" like Inside Airbnb and a "CPI" reading.

### 5.4 Host decisions

Each reviewing dwelling that is not owner-occupied-as-principal-residence chooses among `STR`, `LTR`, `VACANT`, `SELL` using a multinomial logit:

```
U_STR    = a1 * expectedStrNet_z  - legalityPenalty            (+ eps)
U_LTR    = a2 * expectedLtrNet_z                               (+ eps)
U_VACANT = a3 * optionValue - vacancyTax                       (+ eps)
U_SELL   = a4 * saleProceeds_z(interestRate) - transactionCost (+ eps)   [SELL converts to OWNER_OCC]

expectedStrNet_z  = occupancy_z * nightlyRate_z * 30 - platformFee - upkeep
expectedLtrNet_z  = marketRent_z * (1 - expectedVacancy_z) - upkeep
legalityPenalty   = 0 if legal else  (detectProb * fine) + (1-complianceBase) * 0 + delistRisk * lostRevenue
```

Legality:

- In a **covered** zone after Phase 1, an STR is legal only if `principalResidenceOfOwner`. Non-principal-residence STRs are illegal and face `detectProb` (a function of enforcement budget) and `fine`.
- After Phase 2 (registry + platform de-listing), illegal listings are removed with probability `delistProb` (near 1) and legal listings must register at cost `registrationCost` and delay.
- `compliance heterogeneity`: host classes differ. COMMERCIAL hosts have scale economies for compliance and different exit behaviour (this is what lets the multi-listing-host share fall, target T5).

**Where do displaced units go?** The first project does *not* identify this. Model it as a simplex `(gammaLTR, gammaSell, gammaVacant)` that falls out of the logit utilities but with host-class priors, and **treat the main response parameters as weakly identified**. The calibration pipeline (section 7) returns an *ensemble* of parameter sets, and the game samples from it, so uncertainty over "where did the units go" is visible to the player. This is a feature, not a bug.

**Spillover to exempt zones.** Hosts in covered zones cannot move their dwelling, but investors can *buy* in exempt zones (the SELL → buy flow plus an `investorEntry` process raising STR supply in exempt zones). This matters for the DiD-recovery test (section 8).

### 5.5 Rental market and rents

- Each zone has `marketRent_z`, the asking rent for new leases, adjusting toward balance:
  `d log(marketRent_z) = kappa * (vStar - v_z) + shockRent`, where `v_z` is the zone's LTR vacancy rate and `vStar` the natural vacancy rate (CMHC-informed, ~3%; Victoria 2025 was 3.3% in the first project's fixtures).
- **Sitting tenants:** rent changes once a year on lease anniversary by `min(rentCap, partialAdjustmentToMarket)`. New leases reset to `marketRent_z`. This mimics BC's rent-increase cap and is the reason CPI rented accommodation moves slowly.
- **Two rent indices reported** (this is a deliberate teaching device):
  - `askingRentIndex`: new-lease rents (what an asking-rent dataset would show).
  - `cpiRentIndex`: tenure-weighted average of *all* occupied LTR rents (mostly sitting tenants, like StatCan's "Rented accommodation" aggregate), plus measurement noise (SD from the first project's quarterly CPI noise, about ±3-5 points `[VERIFY]`).
- **Matching:** each month, searching households are matched to vacant LTR units in preferred zones subject to affordability (rent ≤ `maxShare * income`). Unmatched households accumulate `searchMonths`.

### 5.6 Developers and zoning

- Starts in zone `z`: `starts_z = max(0, round(rho * (expectedMargin_z - hurdle(interestRate)) * headroom_z))` where `headroom_z = max(0, capacity_z - dwellings_z - pipeline_z) / capacity_z`.
- Completion lag `L ~ Uniform(18, 30)` months (`[VERIFY]`; default 24). Upzoning raises `capacity_z` after a **permit delay** (default 12 months). Delays make the player feel the lag between decision and outcome.
- New completions enter as LTR or OWNER_OCC by a `rentalShare` parameter.

### 5.7 Households

- Arrivals from migration: a Poisson-like count (hashed RNG) of new households per month.
- `SEARCHING` for more than `kDouble` months → `DOUBLED_UP`; more than `kLeave` → `GONE` (out-migration). These are the "housing stress" outcomes in the score.
- Rent burden = rent / income for housed households; reported as share above 30%.

### 5.8 Policy levers (v1 set)

| Lever | Options | Cost | Notes |
|---|---|---|---|
| STR regime | Open / Principal-residence rule / Principal-residence + registry | Political capital | Matches Phase 1 and Phase 2 mechanics |
| Enforcement budget | 0–5 steps | Fiscal $ per quarter | Raises `detectProb`; diminishing returns |
| Vacancy tax | 0%–3% of assessed value | Raises revenue; political cost | Pushes VACANT toward LTR or SELL |
| Upzoning | None / Moderate / Aggressive per zone | Political capital; permit delay | Raises capacity after delay |
| Rent-increase cap | Low / Medium / High (tied to CPI offset) | Political capital | Low cap: more sitting-tenant protection, slower turnover, possible landlord exit |
| Public/non-market build (stretch) | N units per quarter | Fiscal $ | Direct supply |

**Resources:** each turn grants fiscal budget and political capital. Changing a lever consumes both; some levers cannot be reversed immediately (cooldowns), to reflect legislation lag.

### 5.9 Shock/scenario cards

Drawn at the start of selected turns from a deck (seeded, so reproducible): interest-rate hike, migration surge, recession (income drop), court challenge to the STR rule (enforcement multiplier drops for 4 quarters), tourism boom (strDemand up), wildfire (temporary STR demand and displacement shock). Each card has fixed effects defined in JSON, documented in ODD.

### 5.10 Observation layer ("fog of data")

`observe.ts` produces two views of every run:

- **God view:** the true state each tick (used only at debrief and in tests).
- **Researcher view** (what the player sees in-game): quarterly snapshots of active entire-home listings by zone, with scrape-completeness noise and occasional truncated snapshots (the first project found real ones), plus a noisy `cpiRentIndex`, plus a lagged `askingRentIndex` if the player pays for a "data purchase" action (fiscal cost).

Decisions are made on the researcher view; the debrief reveals the god view. This mirrors the first project's lesson that measurement choices matter.

## 6. Game design

### 6.1 Core loop (per turn)

1. See the **quarterly briefing**: researcher-view charts, any shock card, stakeholder headlines (generated from templates).
2. Spend resources on levers. Previewing a lever shows a **qualitative forecast with an evidence badge** (see 6.3), not a number.
3. End turn → sim runs 3 ticks → map animates (listings change, construction cranes, "for rent" signs).
4. Repeat for 20 turns, then the **debrief**.

### 6.2 Objectives and scoring

A multi-objective scorecard. There is no single correct strategy, and each objective is shown separately:

- Renter affordability: share of renter households paying >30% of income.
- Housing stress: households doubled-up or gone (cumulative).
- Supply: net completions.
- Fiscal balance: revenue (vacancy tax, fines) minus spending (enforcement, build).
- Visitor capacity / local business index: a deliberate counterweight, because STR also supplies tourist beds. Gutting STRs has a cost.
- Political capital remaining.

Optional **Mandates** at start (e.g. "Affordability first", "Balanced budget", "Tourism-dependent region") weight the scorecard differently.

### 6.3 Evidence badges

Every lever and every displayed effect carries a badge tying it to its provenance:

- **Measured here** (from the first project: e.g. STR rule's listing effect).
- **Literature** (cited, in `docs/ASSUMPTIONS.md`).
- **Assumed** (weakly identified, wide uncertainty).
- Plus an "uncertainty fan" on forecasts (from the ensemble).

### 6.4 Debrief (the payoff screen)

- **Your term vs. no-policy counterfactual**, same seed (CRN), with fan charts across N=200 replications run in a Web Worker.
- **What you could have known:** researcher view vs god view, with the measurement problems called out.
- **The Bill 35 lesson card:** "Listings in covered areas fell ~32% after Phase 1, but the data cannot distinguish the rent effect from noise." Link to the first project's dashboard.
- **Did a researcher's DiD get it right in your world?** Run the DiD recovery estimate (precomputed table or lightweight in-browser regression) and compare to the true effect. See section 8.
- A shareable seed + settings string.

### 6.5 Onboarding

First 4 turns scripted: introduce one lever at a time, explain the two rent indices, show one shock card. Skippable. Every term has a tooltip glossary.

### 6.6 UI layout (desktop-first)

Left: isometric map with zone selection and overlays (STR, vacancy, construction, rent burden heat). Right: tabbed panel (Levers, Data, Stakeholders, Log). Top bar: turn, date, fiscal budget, political capital. Bottom: end-turn button and mini-scorecard. Responsive down to tablet; phone is a stretch goal.

### 6.7 Accessibility (required, not stretch)

Colour-blind-safe palette (verify with a simulator), never rely on colour alone (icons + patterns), full keyboard operability, visible focus, `prefers-reduced-motion` respected, minimum 16px UI text, ARIA labels on charts, and text alternatives for key insights.

## 7. Calibration plan (Python, `calibration/`)

### 7.1 Method

**Simulated method of moments / approximate Bayesian computation (ABC).**

1. Define free parameters θ with priors (`calibration/priors.json`): STR utility scale, host-class heterogeneity, compliance probabilities, detection probability by phase, fine size, delist probability, investor-entry rate, and the displaced-unit destination priors (wide).
2. Moment vector m(θ) from the sim, computed from the researcher-style panel *without* observation noise: T1, T2, T3, T4, T5, T6, T7.
3. Distance `D(θ) = Σ w_k * ((m_k(θ) - target_k) / se_k)²` with T2 down-weighted (it is not statistically distinguishable from placebo).
4. **Stage 1:** Latin hypercube / Sobol sample (≥ 5,000 draws, each run is cheap). **Stage 2:** local optimisation (CMA-ES or Nelder-Mead) from the best candidates. **Stage 3:** ABC rejection within a tolerance to produce an **ensemble of 200–500 accepted parameter sets**. The ensemble, not a point estimate, is the product.
5. Each moment is averaged over R replications with *common* seeds across θ to reduce noise.

### 7.2 Outputs (committed)

- `packages/sim/src/params/ensemble.json` with metadata (git hash, priors hash, targets hash, tolerance, date).
- `calibration/reports/calibration.md`: fit tables (target vs. simulated mean and interval), parameter marginals, identification diagnostics (which parameters are pinned down, which are not), figures.
- A test fails if `ensemble.json` metadata does not match the current priors/targets hashes (prevents silent drift).

### 7.3 Identification honesty

For each parameter report the posterior-to-prior contraction. Parameters that do not contract (expected for displaced-unit destinations) are labelled "weakly identified" in the UI and in `docs/ASSUMPTIONS.md`.

## 8. Validation plan

### 8.1 Internal validation

- **Parameter recovery:** simulate with known θ*, run the calibration, check θ* falls inside the posterior (a handful of cases).
- **Face validity:** stricter STR rule ⇒ fewer STR listings in covered zones, monotonic over the lever; more enforcement ⇒ fewer illegal listings; higher rates ⇒ fewer starts; etc. (property tests).
- **Conservation:** every dwelling is in exactly one tenure; every household is in exactly one status; dwellings count changes only via completions; no negative counts, no NaN.
- **Sensitivity analysis:** one-at-a-time and Sobol indices of key outputs (rent-burden share, STR listings, completions) over the ensemble; written to `docs/VALIDATION.md`.

### 8.2 External validation (out-of-sample)

- Hold out a feature from calibration (e.g. fit T1 + T3 + T4, then compare T5 and T6, or hold out Salt Spring's opt-in response). Report the miss honestly.
- Compare the sim's STR-attributable rent effect to the bound S2.
- Sanity-compare `cpiRentIndex` path to the +19.5% S1 band. It will not fit exactly, and the doc should say why.

### 8.3 The DiD-recovery experiment (the signature piece)

`calibration/did_recovery.py`:

1. Run the sim under the Historical Bill 35 policy and under no policy with CRN. The **true causal effect** on covered-area listings = difference.
2. Emit a researcher-view panel (quarterly snapshots, neighbourhood × month, with the noise and truncation process).
3. Estimate the first project's preferred covered-vs-exempt DiD (and the room-type-style variants if implemented) using `pyfixest`, with randomization inference.
4. Compare estimate vs. truth across the ensemble. Vary the **spillover strength** (investor entry into exempt zones, SUTVA violation) and show how DiD bias grows.
5. Write the result to `docs/VALIDATION.md` and a figure for the README. This is a short, publishable-quality finding on its own, and a blog-post candidate.

## 9. Art pipeline (`tools/art/`, generated by code, deterministic)

**Goal:** a charming, consistent, small-palette pixel-art isometric city, produced entirely by scripts so it is original, reproducible and editable.

### 9.1 Specs

- Isometric 2:1 tiles: **32×16 px** ground tile. Buildings are 32 px wide, variable height in 8 px steps.
- **Palette:** 24–32 colours max, defined once in `tools/art/palette.ts` with names (`grass1`, `roofRed`, `water2`, …). Colour-blind-safe for all *meaningful* overlays (STR vs LTR vs vacant use distinct shapes and luminance, not just hue).
- Output: one **sprite atlas PNG + JSON map** in `apps/web/public/atlas/`, rendered at 1× and displayed with `image-rendering: pixelated` and integer scaling.

### 9.2 Approach

- Define sprites as **palette-indexed pixel grids in code** (strings of characters mapped to palette entries) plus procedural variation (hash-seeded window lighting, roof colour picks, tree clusters). the coding agent is good at writing these grids; iterate by looking at rendered output.
- Use `pngjs` (or similar tiny dependency) to write the atlas. A `pnpm art` script regenerates everything; the PNG is committed so the site builds without running art tools.

### 9.3 Asset list

- **Ground:** grass (3 variants), road (straight, corner, T, cross), water (animated 4-frame), shoreline, sidewalk, park, forest, rock, farmland.
- **Buildings:** detached house (4 variants), duplex, townhouse row, low-rise apartment (3 heights), mid-rise, tower, hotel, commercial block. Each has **states**: occupied-LTR, STR (small coloured roof marker), vacant (dark windows, sign), construction (scaffold + crane, 3 frames), under-upzone (stakes/sign).
- **Overlay icons (16×16):** STR key, vacancy "closed", rent-stress heat, enforcement badge, tourist, newspaper headline, political capital, budget.
- **Effects:** construction dust, "for rent" sign flicker, delisting stamp, shock-card icons (rate, migration, recession, court, tourism, wildfire).
- **UI:** pixel panel frames (9-slice), buttons (normal/hover/pressed/disabled), tab styles, sliders, badges for the evidence labels.
- **Font:** use an open-licensed pixel font (SIL OFL), check licence, ship it in the repo with its licence file. Do not use proprietary fonts.

### 9.4 Quality loop

1. Generate atlas → render a **sprite sheet preview page** (`apps/web/public/art-preview.html`).
2. Playwright screenshots the preview and the in-game map at 1× and 3×.
3. the coding agent views the screenshots, lists defects (alignment, palette breaks, unreadable states), fixes, repeats. Do this at least 3 rounds before declaring the art pass done.
4. Acceptance: any building state is distinguishable at a glance at 2× scale in greyscale, and all sprites sit on the iso grid without gaps or overlaps.

## 11. Testing strategy and budgets

- **Unit:** each system function against hand-computed cases.
- **Property (fast-check):** conservation, determinism, monotonicity, bounds (rates in [0,1], counts ≥ 0), CRN invariance, replay equality (run in one go vs. step by step).
- **Golden test:** a small fixed scenario's JSON output is snapshot-tested; changes require an intentional update with explanation.
- **Calibration smoke:** a miniature calibration (50 draws) runs in CI to catch pipeline breakage; the full calibration is a manual `make calibrate`.
- **E2E:** Playwright plays 3 turns, asserts the UI updates, saves screenshots.
- **Performance budgets:** one 20-turn run at default `SCALE` < 150 ms in Node; ensemble of 200 runs < 10 s across 4 workers; initial JS bundle < 400 KB gzipped (excluding atlas); atlas < 300 KB; first interaction < 2 s on a mid-range laptop.
- **CI gates:** lint, `tsc --noEmit`, unit + property tests, build, Playwright smoke. Coverage on `packages/sim` ≥ 85% lines.

## 13. Risks and mitigations

| Risk | Mitigation |
|---|---|
| Model is not fun | M2 prototype before heavy investment; playtest with 3 people before M5 |
| Calibration will not converge or is poorly identified | Ensemble approach; down-weight T2; hand-tuned fallback with the identification limits documented |
| Scope creep (more levers, more zones) | Fixed v1 lever list (5.8); stretch items only after M8 |
| Art eats the schedule | Procedural + palette-limited approach; art pass is time-boxed to a week |
| Misleading the public on rent effects | The honesty rule in section 2 and the "too small to detect" language; evidence badges |
| Silent drift between sim and calibrated ensemble | Hash-checked ensemble metadata test |
| Performance regressions | Budgets in CI via a micro-benchmark with a generous threshold |
| Licence problems | Original art only; OFL font with licence file; attribution page |
